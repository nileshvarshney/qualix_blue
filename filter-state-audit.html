Root Cause — Architectural

All filter state is stored in React local useState — no URL synchronization anywhere in the app

Every module in Qualix (Data Quality, Governance, Operations, Admin) stores filter values, search queries, and selected contexts in component-local React state. No page in the application calls useSearchParams, writes router.push with query params, or reads from sessionStorage. When a component unmounts — triggered by tab navigation, browser back, or a direct URL visit — all filter state is discarded and the page reinitializes to defaults.

This is not 9 isolated bugs. It is one architectural gap expressed 9 ways. Fixing it requires a consistent state persistence strategy (URL params via useSearchParams is the standard Next.js solution) applied uniformly across all filter-bearing pages.

Additional Observations

⚠️
Stored XSS Risk — Glossary Term Name
A glossary term named <script>alert(1)</script> is present in the database and visible in the Glossary list. It is currently rendered as escaped text. Risk: any downstream template that renders term names without HTML sanitization (email alerts, PDF exports, audit logs, tooltip renders) will execute the payload. Verify all term-name render paths.
🔗
Catalog Drawer Has No "View in Lineage" Affordance
The CUSTOMERS asset detail drawer in /catalog exposes connection, schema, columns, history, and linked terms — but no cross-module navigation link to Lineage. Users who want to see the lineage graph for a specific asset must close the drawer, navigate to the Lineage tab, and re-search manually. A "View Lineage" button should be added (see FD-007).
🔍
Execution Log Row Clicks Are Inline-Only — No Permalink
Clicking an execution log row expands it inline with individual rule results. The URL remains /execution-logs — no run ID, timestamp, or table identifier is appended. This makes it impossible to share a specific execution run with a colleague, link to a failed run from an alert, or bookmark a result for later review.
